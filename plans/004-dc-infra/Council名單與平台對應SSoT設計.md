# Council 名單與平台對應 SSoT 設計

本文件保存 [dc infra Plan](plan.md#council-list-與-ssot-維護的接續討論)的設計與取捨。使用者已授權兩項獨立分析同意後，依「本地 repo → Discord」執行本輪範圍；分析已同意，本地實作進行中，尚未發布。下文「建議／預計」保留設計形成時的語境；現行資料規則以[成員識別與資料](<../../specs/01-制度/[規格]成員識別與資料.md#council-名單與維護>)為準，實際進度見 [Plan](plan.md#本輪分析與本地實作)。前輪已採納的 Council 身分與 Moderator 能力分開、沿用既有協作頻道等設計，仍以 [Discord Setup](<../../specs/05-社群基建/[規格]Discord-社群-Setup.md>)為準。本輪補齊維護方式，不指定任職者或授予平台權限。

## 需求與上一版不足

使用者原話：

> 所以 council 表要從哪看？
>
> 你整個提案是不是有一堆 gaps 然後不去想清楚啊
> please peer to peer review and give me the best complete proposal

上一版只說每類資料有唯一來源，卻把入口、資料表示、自動化程度、帳號公開方式及維護接續全部留待討論。它沒有回答「明天換一位 Leader，誰改哪裡、怎樣知道 Discord 完成了」，不能直接交付執行。

本版推薦一個完整範圍：**公開的 Council 表放在 members/council.md，由既有 assignment 產生；任職依據由人核對，程式負責彙整與檢查；Discord 按有效分工逐次操作與核對。** 不要求成員另外維護 Council 身分。

## 要解決的 Problem 與限制

管理者及成員需要直接找到 Council、每人負責什麼、任職依據及尚未完成的接續。現在部分來源未被串起、本機落後遠端、任職與平台帳號對應未核實，容易將列名、文件合併、任職生效和平台操作誤認為同一件事。

維護要保住既有制度：同人兼任只算一人；資料不足不能變成撤任；Council 身分不自動授予 moderation 或技術權限；公開 repo 不收私人帳號證據；已開票的名冊不能被現在的表改寫。有效資格、首屆任命、一般任免、辭任與恢復依[憲政制度](<../../specs/01-制度/[機制] 憲政制度.md>)，資料依[成員識別與資料](<../../specs/01-制度/[規格]成員識別與資料.md>)。

## 打開哪裡、會看到什麼

建議新增 `members/council.md`，標題為「Council 名單與分工」。repo 根 README 與 members README 都直接連入；Discord 既有 onboard 說明加入一個入口連結，不複製人員清單、不新增頻道。Discord 連結須等 canonical repo 的 main 上該頁已發布且可實際讀取後才加入；只完成本機檔案時不貼尚不存在的遠端網址。發布須依使用者授權，尚未發布則保留該步未完成。

Council 表頂部保留一行：**Verify note：Council 必須至少擔任一項有效的 R&R Leader。**

表的頂部固定顯示：

- 這是依所列來源、截至所列核對時間產生的檢視，不是任命文件或即時名冊。
- 任職依據最後核對時間、產生時使用的來源內容摘要值、來源連結。
- 完整性：已核對本次範圍，或仍有哪些任職／身分／後續事件未核對。不能以列了幾個名字就稱全體完整。
- 需要更正時回原 assignment／原案提 PR 或 Issue；不直接編輯產生的表。提案與異議不以特定管理者受理為條件。

正文分為「截至核對時間可確認的 Council」「尚未生效的安排」「任職依據待核對」「待更新」。同一人在有效區只列一行，欄位是姓名與自介、全部有效 Leader 職位、任命及接受依據、各職位生效時間。未生效、待核對及待更新各區另列缺什麼、原案連結、已接受的接續者或「尚未承接」。同一人可有有效職位，也有另一項未生效安排，兩者分別呈現。

空狀態必須區別：完成核對且確實沒有符合條件的人，才寫「截至核對時間未有有效 Council」；資料不齊則寫「尚無足以列入已核對區的資料，不能據此判定沒有 Council」。姓名相同不自動合併，未編 Member ID 不剝奪既有有效資格。

這張表不放敏感報案、私人聯絡方式、完整 Discord 權限快照或投票分母。投票仍由原案依制度建立當案固定名冊；可參考此表，但必須核對截至開票時的全部有效事件。

## 來源如何分工

| 內容 | 唯一維護位置 | 其他地方怎麼使用 |
|---|---|---|
| 本人稱呼、Member ID、GitHub 與自介 | 現有個人成員檔案 | assignment 引用同一人，Council 表從來源帶出 |
| 入會、首屆成立、任免、接受、辭任及恢復的原始事實 | 原 PR／Issue／有效決定；首屆沿用 Kickoff | assignment 只放來源索引與本次任職核對結果，不另建資格流水帳 |
| Leader 與 Contributors 安排 | members/r-and-r-assignment.md | Council 表由此產生，個人自介不重抄職位 |
| 各職位的責任與必要能力 | 既有 Role 與平台規格 | 操作者據此準備本次具體權限差異 |
| Discord 當下帳號與實際權限 | Discord 當下設定與本人確認 | 每次操作重新核對；公開原案只記必要結果、未完成事項與接續者 |
| Council 閱讀入口 | members/council.md，產生檔 | 不允許另手填 Council 布林值或維護第二套名單 |

Council 表只能顯示已登錄且有核對依據的結果，不能創造任職。有效原案與表不同時，回原案確認並更正來源；文件晚合併不延後原本已依法生效的職權，也不能延長已終止的職權。

## assignment 的最小調整

保留既有每個 R&R 一節、Leader 與 Contributors 分開的格式，不遷移整批 YAML，不改新人填 Contributors 的方式。在每個 Leader 區塊使用一致欄位，讓人和程式都能讀：

- 人員：連到個人成員檔案；已有 Member ID 從個人檔案核對，不另配置。
- 決定依據：原案及精確結果位置；首屆共同生效沿用同一份原案。
- 本人接受：原始確認位置及所接受範圍。
- 生效條件：依原案，還沒發生的條件直接寫明。
- 生效時間：ISO 8601 日期時間，含 +08:00，尚未確定則明列「未定」。
- 核對截止：ISO 8601 日期時間，含 +08:00；核對紀錄須涵蓋截至該時點的相關事件。
- 本次核對：原案中的核對紀錄連結、核對人、核對時間及適用來源版本。
- 核對結果：截至該時點已生效／尚未生效／依據待核對／已終止。這是對原案的整理，不是新增裁決權。
- 尚未完成：缺少依據或要接續的操作，連回原案及本人已接受的接續安排。

建議固定欄位範例（示意，非真實任命）：

```markdown
### Leader

- 人員：<個人成員檔案連結>
- 決定依據：<原案結果永久連結>
- 本人接受：<接受紀錄永久連結>
- 生效條件：<原案條件>
- 生效時間：<ISO 8601 含 +08:00，或未定>
- 核對截止：<ISO 8601 含 +08:00>
- 本次核對：<核對人、截至時間、來源版本、原案核對紀錄連結>
- 核對結果：<已生效／尚未生效／依據待核對／已終止>
- 尚未完成：<具體事項、原案連結、已接受的接續者或尚未承接>
```

有現任與未來接任時，每人一組上述欄位，程式按共同核對時點檢查不能重疊；未完成資料不得用空字串偽裝通過。完全尚無人選時，沿用「待確認」並解析為空缺，不要求虛構人員。已終止的歷史區塊不作目前候選。相同人優先以永久 Member ID 比對，未配置時用正規化個人檔案路徑；跨檔帳號重複或身份疑義只報錯，不自行合併、另發編號或取消資格。

資格核對紀錄留在原案，說明適用的一般入會、首屆、過渡或恢復依據，以及核對過哪些後續有效事件；不能只看一次 PR 合併。本次任職區塊引用該紀錄，不在個人檔案或新的資格總表重抄 active 狀態。單純「有 URL」或「有人說已核對」不能代替可查核理由。

既有結束安排可留在該職位明確標示的歷史區，原始經過由 Git／PR 查回；目前有效職位和未來接任要能並列，不能因先填接任者就覆蓋仍有效的原任。程式遇到同職位在同時點兩位有效 Leader、身份衝突或不支援的排版，要報錯且保留上一份明示時點的表，不猜測哪個人勝出。

## 誰做、怎麼接續

**整理資料：**原案已接受工作的承接者，在任職生效、辭任、替換或來源更正時，提出同案的 assignment 更新；沒有已接受者就在原案明列尚未承接。任何正式成員可依原案整理核對；AI 可協助準備，不作資格或爭議的最終裁決。整理者在原案留下來源、適用時間與未完成內容。這不是新增一個所有任命都要等人簽名的審查關卡。

**成員資格及帳號：**Onboard 依既有職責提供資格資料與本人對應；有疑義依司法與覆核及非涉案備援程序。沒有合格者時揭露受阻，不能讓 Repository、AI 或任意 Contributor 取得裁決權。對已有明確有效結果的抄錄，不要求重新審一次入會或任命。

**檔案與工具：**Repository 在既有技術維護範圍內接續 renderer、CI 與必要文件整合。資料 PR 由有合併權者依有效依據處理；合併不代替治理決定。新增共同維護義務須按制度採納，不能用此提案直接強派工作。

**Discord 操作：**具該平台有效操作職責、實際能力且無須迴避的人依原案執行。人事案當事人不能核准、覆核或執行自己的利益案件；本人可提供資料與接受職責。

**沒有人接手：**在同一原案明列缺哪一項接續、原有有效任職和平台風險；有合格備援才交接，否則依制度補任或平台正式恢復方式處理。不能寫「交給 Repository」就假裝已有真人接受。

一般資料更新以原案的承接安排為準，不虛構每日／每週固定義務。職位終止的既有要求仍適用：決策權立即停止，具有效操作職責者二十四小時內啟動撤權／移交，以七十二小時完成為目標。不得因等待報表、CI 或 PR 合併而延誤。確實受阻要留下原因和接續，不把目標寫成完成保證。

## 產生、檢查與過期處理

建議新增 `scripts/render_council.py`，提供兩個明確操作：產生 Council 表，以及 `--check` 比對目前來源與產生檔是否相符。程式讀固定格式的 assignment 與所引用個人資料；核對欄位、內部連結、身份唯一性、同職位重疊及產生檔差異，依核對時間彙整已由人整理的結果。它不靠抓網頁或 AI 推論判定法律／制度效力。

每次產生須顯式指定一個共同核對截止時間，不從執行當下自動填今天。只有核對截止等於本次共同截止，且原案核對紀錄以該時點為準的職位才能進已確認區；不同截止的資料均進「待更新」區，保留原核對時點，整表標示尚未完整。須回查共同截止時的實際狀態才能列入，不能以今天已終止的結論代表昨天。舊任昨日有效與接任今日有效不能先混合再判成同時重疊。程式檢查截止、固定狀態與明確時間欄位，不解析自由文去斷言生效條件滿足，也不因時間到達自動把尚未生效改成有效。

資料更新者在同一 PR 修改來源並重新產生表。CI 只讀執行 `--check`，不需要 Discord token，不寫 main、不派角色。來源未改但手改產生檔同樣檢查失敗。產生檔記錄實際輸入內容摘要值，避免用「包含它自身的 commit」造成反覆改檔；原案核對版本及時間另有來源。

CI 通過只證明表與輸入一致，不證明所有外部原案已查完。新的辭任、未來生效時間到達、原案更正或有效暫停，都須由承接者核對並更新來源；未有接續者就明列尚未承接。未來時間到達不能靠舊報表自動宣告已生效，因為其他條件可能仍未成立。

開票前、權限操作前及交接時，執行者必須重新看原案及後續事件，不能只拿昨日產生檔當現在。資料取不到時保留原時間與未完成範圍；不重新蓋上今天時間，不產生空名單覆蓋舊表，也不撤權。網頁或外部紀錄已知更新但尚未核對時，表需顯示待更新；尚未被任何人發現的外部事件無法由靜態 Markdown 自動偵測，本版不宣稱具備即時保證。

## Discord 帳號與權限怎麼對應

第一階段不把 Discord User ID 設成所有成員必填，也不先建立尚無人維護的私人資料庫。**新增權限或更換綁定時才要求當次本人確認；公開 Council 名單不依賴 Discord 綁定才能成立。**

新增權限或換綁時，操作者從本人已可核對的 GitHub 身分與 Discord 互動雙向確認；讀取 Discord User ID，不能只看暱稱、頭像或相同顯示名稱。具體採一次性確認字串或雙向確認留言皆可，但必須可證明兩邊是同一位本人且是本次確認；不要求私人證件。公開只記錄哪位操作者在何時核對誰、是否完成與原案；未經本人同意不貼 Discord 數字 ID、私人訊息或聯絡資料。

涉及私訊的核對只在本人及有權、非涉案的操作者可存取之原對話進行，不另拷貝進 public repo。新增或換綁時若無法合法交接或原對話不可得，就重新核對，不把一份不可查核的「已綁定」永久沿用。撤權則按下段處理，不以取得離任者新同意為前提。這會多一次核對，但能先運作且不引入新的私人名冊管理成本；將來若確有頻繁管理需求，再另比較受控共享來源及其持有人、存取與退出規則。

撤除已明確對應且原有效職責已終止的能力時，依原核對證據、既有配置與當下不可變 User ID 辨認帳號，不要求離任者再次同意或回覆。原操作者可提供不含秘密的核對結果，需查看原始證據時限有權且非涉案者；不能因私人對話無法移轉就強迫公開。確實缺乏足以識別的證據時，明列本項受阻並依既有備援／恢復程序處理，不靠姓名猜測或擱置已知正確帳號的撤權。此首階段不提供跨管理者永遠可用的私人綁定儲存；交接時須實際驗證所需證據可供合法查核，否則平台接續不能列為完成。

每次先讀 Discord 當下設定，列本次對象、已有角色、有效職責所需能力及確切要加撤的差異。Council 僅標識／通知；Moderator、Repository 技術能力與接續能力分別核對。角色層級、頻道覆寫及既有其他角色都要一起看，不能只驗證角色名稱。

只撤失效職責帶來的能力；仍有另一有效職位需要同一能力時保留。若角色設計把多種職責綁在一起，先拆清能力與合法接續，不能一鍵撤掉一般成員交流權益。若無權修改、帳號尚未加入伺服器、對應有疑義或需本人迴避，留下本項受阻，不動其他人的權限。

操作後回讀；部分成功就逐項記錄已完成與未完成，重試先查當下狀態，不能重複盲加或盲撤。設定誤改時僅恢復仍有有效依據的能力，不能為了回復舊狀態重新授予已失效權限。公開原案保存非敏感結果與接續，截圖和原始驗證輸出只在不版控的本機位置。

## 首次建立怎麼做

1. 先取得最新遠端與本機差異，保留其他人的工作。以遠端來源核對 Sun、品毅、水球等既有安排，不用本機較早的「待確認」否定新資料。版本事實見 [Plan 現況](plan.md#已查到的現況)，這不是本輪重新驗證所有人的任職。
2. 沿原始 PR、有效制度採納與 Kickoff 核對首屆完整名單、本人接受、共同生效時間、正式成員依據及後續任職事件；首屆逐人核對自介、接受憲法、Contributors 選擇、職責接受與必要權限配置。尚未生效的 Onboard 或 Council 不替自己核准成立。原始資料若已存在就補引用；若從未成立，依原適用程序補齊，不能倒填日期或用這次 commit 替代。
3. 對每項安排標示可確認、未生效或待核對，明確留下缺少的事實與已接受的接續者。初始表可先公開有界線的現況，不能為了趕出「完整名單」冒稱全部成立。
4. 補固定格式及 renderer，產生 Council 表，核對每人只一行、每職位都有來源，再加入入口與 CI。缺欄位是需處理的資料問題，不是開除名單內的人。
5. 沿已有效的操作責任逐項核對 Discord 身分、Council role、技術接續與 moderation；分別完成，不因名單完成就把後三項勾選。第二位技術接續者、警示接收者、敏感聯絡人與獨立覆核仍須本人接受、有效職責及實際能力。

「成立首屆」不是每次工具遷移都能重啟的捷徑。外部有有效依據但 repo 尚未承接時，先取回來源；沒有來源時明示未知，不自行宣布全部人無資格。

## How to test

以明示測試資料驗證工具，以真實原案驗證資料維護；兩者不能互相冒充。

- 同一人兼兩個有效職位，Council 一行列兩職；只結束其中一職仍保留，最後一職結束才從該核對時點的有效區移出。
- 兩人同名不誤合併；編號尚未配置但原資格有效仍有可追溯呈現；無法辨認時報出疑義。
- 未來任命、缺接受、缺共同生效、資格來源不全各顯示具體原因；資料缺漏不觸發撤權。
- 修改 assignment 或自介但未產生表、直接手改表、重疊有效 Leader 或解析失敗，都有具體失敗訊息；不發布空表。
- 先辭任後補登錄，制度生效時間不改成合併時間；接任未生效時原任仍有效的安排不被提前覆蓋。
- 開票後發生合法職位變動，現在 Council 表可變，原案固定名冊不回算；原資格錯誤按既有覆核規則處理。
- 同一張表混入不同核對截止時，較舊職位顯示待更新，不能冒稱共同時點完整；程式不從自由文或時間經過推導生效。
- 離任者不回覆但原帳號對應已明確，仍能依法接續撤權，不把新本人確認當成阻擋。
- Discord 對應錯人、未加入、缺操作能力或部分加撤失敗，不能顯示全部完成；操作後確認能力與有效職責相符、其他權益保留。
- 保留四個入口唯讀、公開交流權益及敏感內容限制；Council 本身不新增管理能力。
- 從根 README 或 members README 一次進入 Council 表，從任一人找到有效職位與原案；新人仍能直接用原 Contributors 流程。

工具完成、名單核實、正式程序完成及平台操作完成分開交付。尚缺真實首屆依據或承接人，不妨礙完成提案或只讀工具，但不能宣稱組織權限接續已完成。

## 取捨與採納邊界

不選另一張人工 Council 表，因為會與 assignment 分歧；暫不把全部資料改成 YAML，因為現有分工欄位已能承載；不建自動賦權 bot，因為任職判斷、身分核對與覆核不能由欄位取代。代價是原案仍需人核對、按次綁定較花操作時間、靜態表不能即時感知外部事件。這些限制在入口與執行流程明示，不能包裝成已完成的自動化。

本次請採納的是上述完整維護設計；實際人員接受、首屆有效依據與每次平台操作仍以真實來源辦理。設計選擇已給出明確推薦，不把路徑、格式、公開方式和自動化程度留成四道空白題。尚缺的是現實中的有效證據與承接，不由 AI 補造。
